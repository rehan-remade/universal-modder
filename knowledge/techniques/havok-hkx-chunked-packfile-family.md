# Havok HKX: the chunked packfile family across game generations (and when you need the SDK)

> Havok ships two very different on-disk shapes: the **classic binary packfile** (one flat object
> graph, FO4/Skyrim era) and the newer **chunked tagfile** (`TAG0/SDKV/...`, 2015.1 onward). Reading a
> modern chunked file is usually just parsing; *converting* between versions, or reading a
> vendor-customized variant, needs the matching `hkCompatFormats.dll` — and that is where most projects
> get stuck. This note records the version→format mapping and the parser set that actually works.

## When to use it

Any time you meet an `.hkx`/`.hkr` and need to know (a) which Havok version wrote it, (b) whether a
public parser can read it, and (c) whether you are looking at a format problem or an SDK problem.

## How

### Identify the version first

| Game / asset | Havok version | Format |
|---|---|---|
| Fallout 4 | **2014.1.0-r1** (v11, 64-bit LE) | classic binary packfile |
| Skyrim SE | **2010.2.0-r1** (v8, 64-bit LE) | classic binary packfile |
| Watch Dogs: Legion — retail assets | **2017.2.0** (`SDKV="20170200"`) | chunked tagfile |
| Watch Dogs: Legion — leak/dev tree assets | **2015.1.0** (`SDKV="20150100"`) | chunked tagfile |
| Watch Dogs: Legion — some vehicle collision | **2014.2.5-r1** | classic binary packfile |
| Starfield — physics/collision | **2019.02** (`SDKV="20190200"`) | chunked tagfile |
| Test Drive Unlimited 2 — vehicle + level/scenario collision | **5.5.0-r1** (v5, 32-bit LE) | classic binary packfile |

**The single most useful check:** the chunked tagfile carries its version in a literal `SDKV` chunk.
Decode that and you know the writer. Do not trust "the wiki says 2017.1" — real WDL retail assets
measured `20170200`, which corrected an earlier documentation error.

### The chunked tagfile shape

Standard chunked files are a sequence of four-byte-magic chunks. The tags seen in the wild:

`TAG0`, `SDKV`, `DATA`, `TYPE` (with sub-tags `TPTR`, `TSTR`, `TNA1`, `FSTR`), `BITS`, `STORAGE`,
`ENUM`, `VALID`, `ITEM`, `PTYPE`, `ITYPE`, `MASK`, `INDX`, `PTCH`.

Starfield's 2019.02 and WDL's 2017.2.0 are the **same structural family** — a parser written for one
reads the other. The `StarfieldMeshConverter` parser is the reference implementation for both.

### Two serialization modes for a vendor-customized Havok

Disrupt-engine titles (Watch Dogs) use a **custom Havok**; a stock commercial SDK cannot render their
files. Two shapes appear:

- a **compact** layout (uses `TCRF`-style packing), and
- a **portable** layout (`TYPE`/`TNA1` self-describing).

Dev-tree SUV collision measured as the portable layout; that is the readable one.

### Parsers that work without an SDK (reading)

- **`hkxpack`** (Java, MIT) — original reader.
- **`hkxpack-plus`** (Java, MIT) — 910 bundled class definitions; the best validation tool.
- **`HKX2-Enhanced-Library`** (C#) — 589 autogenerated classes; most complete.
- **`havoklib`** (C++, GPL), **`blender-hkx`** (MIT), **`hkdump`** (C++, MIT).
- **`hkxcmd`** — "Havok Command Line Tools 1.4", Skyrim `HKX <-> XML/KF`.
- **`StarfieldMeshConverter`** — full chunked parser for 2019.02 (also the WDL 2017.2 reference).
- **`tagtools`** — `TagTools.py` + `TypeDatabase.xml` for tagfile inspection.

### Exporters (writing)

- **`HavokAnimationExporter` (HAE)** (C#, `blueskythlikesclouds`) — generates **skeleton and
  animation HKX** from FBX for Sonic titles; the rare public case of a *writer*, not just a reader.
  Options: `-s/--skl` skeleton HKX,
  `-u/--uncompressed`, `-f/--fps` (default 60), platform `-w/--windows`, `-x/--xbox360`, `-p/--ps3`,
  `--wiiu` (2012.2.0 only), `-t/--tagfile` (2010.2.0 / 2012.2.0 only). Sonic-specific caveats: new
  bones need the `@NEW` tag (Unleashed); root animation unsupported; Sonic Forces needs tagfile output
  plus a TagTools backport of the skeleton.

### When you actually need the SDK

Reading self-describing portable/chunked files needs no SDK. **Converting** between Havok versions —
and reading a compact/vendor variant — goes through `hkCompatFormats.dll`. Empirical result:
the Ubi-shipped Havok Content Tools **2017.2.0-r1** runs, but with a missing/mismatched
`hkCompatFormats.dll` it refuses the very assets it should convert:

- SUV 2017.2.0 chunked → `[s11n.Serialize] The format was not recognized (hkSerialize.cpp:419)`;
- truck 2014.2.5 packfile → access violation `c0000005`.

Building the missing 2017.2 `hkCompatFormats.dll` from a newer SDK **failed**: the conversion
implementation module (`Tools\FileConvert\CompatFormats\compatLoad`) is not shipped, the configure
script is Python-2 only. The conversion source present in the SDK is
a *patch library* only, not a runnable filter.

Havok SDKs are licensed; don't plan on one. The 2015–2017 SDKs in particular are not reachable, so
for WDL-era assets, prefer parsing the self-describing portable form and skip the SDK conversion path
entirely.

### Reading a 5.5.0 classic packfile: the file is self-describing, so parse the reflection

Old packfiles (5.x) are rejected by every public reader, and the matching-era Havok Content Tools
are a licensed build — not something to depend on or redistribute. The good news is you don't need
them: the packfile **carries its own class reflection**, so a parser can be written from the bytes
alone.

Observed layout (TDU2, `fileVersion 5`, 32-bit LE):

- **0x40-byte header** — magic `57 E0 E0 57` / `10 C0 C0 10` at 0 and 4, `userTag` at 8,
  `fileVersion` at 12, a layout byte each for `bytesInPointer` / `littleEndian` / `reusePadding` /
  base-class-optimization at 16 (TDU2: `04 01 00 01` = 4-byte pointers, LE, no padding, base-class
  optimization on), `numSections` at 20, `contentsSectionIndex` at 24, `contentsSectionOffset` at 28,
  the class-name section index at 32 and its offset at 36 (TDU2: 0xE4), the 16-byte contents version
  string (`Havok-5.5.0-r1`) at 40,
  and `flags` / `maxPredicate` (both `0xFFFFFFFF`) at 56 / 60.
- **Section table at 0x40** — one 48-byte entry per section: a 19-byte name tag, a `0xFF`
  separator, then seven `uint32` fields — `absoluteDataStart`, `localFixupsOffset`,
  `globalFixupsOffset`, `virtualFixupsOffset`, `exportsOffset`, `importsOffset`, `endOffset`. The
  offset fields are **relative to that section's `absoluteDataStart`**, and the sections are
  contiguous: for TDU2, `__classnames__` 208+1280, `__types__` 1488+23584, `__data__` 25072+7040 =
  32112 = the whole file. That arithmetic is the cheapest check that a slice has the right length.
- **`__classnames__`** — a pool of records: `uint32 signature` + a constant `0x09` marker byte + a
  null-terminated name. TDU2's 1280-byte pool holds 54 records and consumes exactly its length, e.g.
  `0x1b58f0ef`→`hkpPhysicsSystem`, `0x3224de76`→`hkpRigidBody`, `0x090cd72e`→`hkpListShape`. Every
  class-name offset (the header field, and the virtual fixups) is relative to the start of this
  section — not to the file.
- **`__types__`** — the `hkClass` reflection: every class's name, parent, size, enums and members
  (member name, type, subtype, `cArraySize`, flags, offset). This is what makes a generic reader
  possible — you read the class layout from the file instead of hard-coding a version's registry.
- **`__data__`** — the object graph, laid out per the reflection above. Every pointer is a
  section-relative offset repaired by one of three fixup tables, each reached from its
  `…FixupsOffset` in the section table and each holding offsets relative to its own section:
  - **virtual fixups** — 12-byte records `(uint32 srcOffset, uint32 sectionIndex, uint32 dstOffset)`,
    one per object, i.e. a class-name pointer. Verified on TDU2: the object at `__data__`+0 has
    `(0, 0, 228)`, and `__classnames__`+228 is `hkpPhysicsSystem` (the root object); 40 objects gave
    40 records, mapping the repeat offenders to `hkpBoxShape` / `hkpConvexTransformShape`.
  - **local fixups** — 8-byte `(srcOffset, dstOffset)` pairs within the same section, ended by a
    `0xFFFFFFFF` sentinel.
  - **global fixups** — 12-byte `(srcOffset, dstSectionIndex, dstOffset)` triples, also
    sentinel-ended, for pointers that cross sections.
  Stop at the sentinel or at the table end, not by dividing the span: the tables are 16-byte
  aligned (measured on TDU2 `f430`'s `__data__`: local 5904, global 5968, virtual 6560, exports
  7040), so span ÷ record size can be off by one. In that section the local span is exactly 64
  bytes (8 pairs); the virtual span is exactly 480 (40 × 12, matching the 40 objects) and has
  **no sentinel** at all; and the 592-byte global span is 49 triples plus a 4-byte `0xFFFFFFFF`
  sentinel (592 = 49×12 + 4), with no padding after it.

A minimal reader therefore: parse the header → walk the section table → read `__classnames__` →
decode `__types__` into a class registry → decode `__data__` against that registry, applying the
virtual fixups to bind each object to its class. That is enough to read TDU2's vehicle physics
(a `hkpPhysicsSystem` with 4 rigid bodies, 4 limited-hinge wheel constraints, and a chassis
`hkpListShape` of 13 box/convex child shapes) with no Havok SDK at all.

### Writing one back: match the header's `layoutRules` to the target

At minimum, the four rule bytes at header offset 16 —
`bytesInPointer`, `littleEndian`, `reusePadding`, `emptyBaseClassOptimization` — must be written to
match the target, and the fixup tables are *regenerated from the object graph*, not copied. Havok's
own `AssetCC` demo converter takes the four as one argument (`--rules4101`) and rejects anything
other than `[48][01][01][01]` ("Rules must be of the form [48][01][01][01] e.g. 4101"; first digit 4
or 8, the rest 0 or 1). Getting it wrong for the target is the classic self-inflicted wound: writing
the console rules on a PC packfile produces a file with the right size and the right (palindromic)
magic in which every multi-byte field is byte-swapped. `AssetCC` is cited here only as the SDK's
reference behaviour for the rules argument; it was **not** the tool used for the round trip below.

The round trip below was verified **off-game only**, on TDU2 `5.5.0-r1`, with our own unpublished
local writer (`parse_hkx.py`): XML → binary with `04 01 00 01` → binary → XML — same
32112-byte size as the source, reads back to the same object graph, and the re-extracted XML matches
the original except for `-0.000000` → `0.000000` (negative zero). 357 of 32112 bytes differ, all of
them either those signed zeros or 4-byte slots inside the rigid-body/motion structs that never appear
in the XML — members the format marks as non-serialised (cached motion-state / swept-transform data a
loader recomputes), which the writer leaves at their defaults.

The useful loop that follows: extract from the container → XML → edit a shape transform or a wheel
hinge axis → binary with the source's own rule bytes → back into the container. Off-game round trip
only; the in-game load is still the oracle.

## Gotchas

1. **`SDKV` is the ground truth.** **Symptom:** docs disagree about a game's Havok version.
   **Cause:** old community notes and vendor trees differ from retail. **Fix:** decode `SDKV` from a
   real retail asset; 2017.2.0 for WDL retail, 2015.1.0 for the leak, 2019.02 for Starfield.
2. **"Same chunk tags" ≠ "same version".** **Symptom:** a 2017.2 parser reads a 2019.02 file fine,
   but conversion still fails. **Cause:** the tag *family* is shared; the *version* and the compat
   filter are separate. **Fix:** identify by `SDKV`, not by tag list.
3. **A classic packfile hides among chunked assets.** **Symptom:** a "WDL HKX" won't parse as a
   tagfile. **Cause:** WDL mixes a 2014.2.5 **classic packfile** (vehicle collision) with 2017.2.0
   chunked. **Fix:** check the first bytes — classic packfiles start with magic
   `57 E0 E0 57 10 C0 C0 10` and the version string `hk_2014.2.5-r1`; `1E 0D B0 CA CE FA 11 D0` is the
   pre-2015 binary-tagfile magic, a different animal.
4. **The SDK's prebuilt libs are not enough.** **Symptom:** `hkCompatFormats.dll` present but
   conversion still fails. **Cause:** the shipped `hkCompatFormats.dll` may be for a different version
   (a PDB path showed `D:\Development\2015_1` for one). **Fix:** verify the DLL's own version; a
   2015.1 DLL will not serve 2017.2.
5. **A newer SDK can still support an older target.** **Symptom:** you only have the 2018.1.0 SDK and
   need 2017.2. **Cause:** you assumed you needed the matching SDK. **Fix:** 2018.1.0's
   `hkHavokVersions.h` lists `HK_HAVOK_VERSION_201720r1 = 60`, and `Compat/Patches/2017_2/` contains
   the 2017.2 patch source — but the *conversion tool* still needs its implementation module, which is
   absent. Support in headers ≠ a buildable converter.
6. **The exe's version-registry list is not the game's version.** **Symptom:** `strings` on the
   executable yields `Havok-3.0.0` … `Havok-5.5.0-r1` and you cannot tell which one it runs.
   **Cause:** that list is the *compatibility* registry (every version the serializer can read), and
   the runtime "built with version [x]" message is assembled at run time. **Fix:** read the version
   string out of a real asset instead. For a classic packfile it sits at header offset 40 (see the
   TDU2 recipe below); the last entry of the registry list is a hint, not proof.
7. **Havok data can live inside a vendor container, not a `.hkx`.** **Symptom:** no `.hkx`/`.hkr`
   files anywhere, so you conclude the game has no Havok. **Cause:** the data is embedded in an
   engine archive. **Fix:** grep the archive for the classic packfile magic
   `57 E0 E0 57 10 C0 C0 10`; TDU2 hides its vehicle physics inside `KNAB` `.bnk` containers
   (magic at offset 0x08), stored uncompressed so it is greppable in place. Not every container has
   Havok: TDU2's `__Unknown/` folder (132 files) is only RIFF/WAVE audio, `KNAB` blobs and `IGE2`
   files — zero Havok signatures.
8. **Every public parser rejects old 5.5.0 packfiles — write your own from the reflection.**
   **Symptom:** `hkxpack`/`hkxpack-plus`/`HKX2` all fail on a TDU2 vehicle `.hkx`
   (`hkxpack` prints `[SEVERE] Could not find file for hkpPhysicsSystem.`). **Cause:** these readers
   only bundle class definitions for 2010.2.0-r1 / 2014.x. **Fix:** don't reach for the licensed-era
   SDK; parse the file directly. A 5.x packfile is self-describing — read the `__types__` reflection
   into a class registry, then decode `__data__` against it, so you never hard-code a version.
9. **A byte-exact repack can still be unreadable — check endianness first.** **Symptom:**
   you write the binary back, the size and the magic match, but the reader crashes. **Cause:** the
   rule bytes at header offset 16 were written for the wrong target (console rules flip every `uint32`
   in the file), and the magic `57 E0 E0 57 10 C0 C0 10` is byte-swap-invariant — so a "the magic is
   right" check proves nothing. **Fix:** copy the source header's four rule bytes back unchanged
   (`04 01 00 01` for a 32-bit LE PC packfile), then verify by *reading your own output* and diffing
   the result, not by eye.

**Reading a classic packfile's version by hand:**

```
off=$(grep -abo $'\x57\xe0\xe0\x57\x10\xc0\xc0\x10' <file> | head -1 | cut -d: -f1)
dd if=<file> bs=1 skip=$((off+40)) count=16      # -> "Havok-5.5.0-r1"
dd if=<file> bs=1 skip=$((off+12)) count=4 | od -An -tu4   # -> file version (5)
```
